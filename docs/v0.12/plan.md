# v0.12 方案：按角色、场景找图，一轮之内的截图也换成占位

> 状态：草稿，等用户确认（2026-11-22）。规格以 [spec.md](../spec.md) 为准，实现见 [design.md](../design.md)。PDF 放到下一版（第 9 节）。

## 1. 背景与目标

- **面板太乱**（用户 2026-11-22）：
  - 筛选按钮那一排是特征行的第一段（v0.8 写场景，10-21 起写地点）。模型起的名字五花八门（“深蓝雨夜”“分镜脚本”“参考网站”），再加上“上传”“生成”两个来源按钮，看不出结构。
  - 图按轮排，可创作时没人记得哪张是第几轮出的。
  - 用户想要的是：找角色，能看到这个角色的脸部特写、多视图；找场景，能看到这个地点的所有图。
- **computer use 的截图没人管**：插件只把之前各轮的图换成占位，当前这一轮的图原样发送（`core/plan.ts` 的 `earlier`）。computer use 常在一轮里连拍几十张截图，这一轮的每次请求都带着全部原图。图最多的场景，插件反而不管。v0.10 第 8 节第 3 条把“截图的规则”留到以后另议，就是这件事。
- **目标**：
  1. 面板按固定的几类浏览：角色、场景、界面、文档、其他，再加一个时间线。
  2. 模型在特征行里写下类别和名字，面板靠它分组，压缩之后也还在。
  3. computer use 的截图在一轮之内也换成占位。
  4. 做一份新的公开评测：用 Sonnet，有压缩压力，给出指标对比，并控制额度。

## 2. 特征行

### 格式

```
[//]: # (cam IMG-015 场景:雨夜街头｜林夏、阿橘｜中景，打红伞)
```

- **三段**：`类别:名字｜画面里的角色｜看得见的特征`。画面里没有角色时，省掉中间一段：`界面:淘宝·订单页｜弹窗，地址未填`。
- **类别只有五个**：
  - **角色**：反复出现、长相要保持一致的对象。人、动物、机器人、怪物、吉祥物都算，做产品片时产品也算。
    - 名字用用户起的；没起名就用外观叫法（“橘猫”“红色机器人”），之后一直沿用。
    - 设定图（脸部特写、多视图、全身）写成 `角色:名字`。
  - **场景**：故事里的地点。名字沿用现在的地点规则：具体到能和别处分开；场次、版本、用途不写进去；时间、天气写在特征里。
  - **界面**：电脑、手机或浏览器上的画面，包括操作截图、自己开发的网页和 App、设计稿。
    - 名字写“应用或网站·页面”，例如“淘宝·订单页”“系统设置·网络”；自己开发的软件直接写页面，例如“登录页”。
    - 写网站名，不写网址。
  - **文档**：PDF 页面、扫描件、幻灯片、图纸、表格截图。名字写文件名或文档名，页码跟在后面，例如“租房合同 第3页”。
  - **其他**：分镜拼图、色板、情绪板、图表等。名字写它是什么，例如“分镜”“色板”。
- **角色段**：画面里出现的角色，用“、”隔开。只写反复出现的角色，不写路人。
- **长度**：40 字以内（原来是 30 字）。
- **连续截图合写一行**：同一个界面连续几张、只有细小变化的截图，可以合写一行，这几张共用这一行：

  ```
  [//]: # (cam IMG-020~IMG-034 界面:淘宝·订单页｜逐步填写收货地址)
  ```

  只用于截图；关键帧、抽帧还是一张写一行。
- **不变的部分**：评价和更正的写法；行写在最后那条回复的开头；正文里不提这些行。
- **英文版**：类别是 `character`、`place`、`screen`、`document`、`other`，段之间照旧用 ` | ` 分隔。

### 旧格式照常认

v0.8 到 v0.11 写的 `地点｜特征` 照常认，按第一段归类：

| 第一段 | 归到 |
|---|---|
| 角色 | 角色，名字记为“未命名” |
| 物品 | 其他 |
| 文档 | 文档 |
| 网页 | 界面 |
| 多个地点 | 其他，名字记为“分镜” |
| 其余文字 | 场景，第一段就是地点名 |

升级之前已有的图仍然不补写。

### 说明怎么改

- 特征行说明（`core/words.ts` 的 `featureNote`，中英两份）按上面重写，每个类别给一个例子。其余规则不变：写在哪儿、一图一行、照原话记评价、正文不提。
- 占位和压缩后的清单照旧原样带上这一行，机制不变。

## 3. 面板

### 从上到下

1. **标题行**：不变。Codex 里仍有“停用插件”按钮。
2. **搜索框**：不变。
3. **分类按钮一排**：`角色 6`、`场景 4`、`界面 12`、`文档 3`、`其他 2`、`时间线`。
   - 这一排取代原来的筛选按钮（全部、上传、生成和各个地点）。
   - 只显示这个任务里有图的类，顺序固定，一次选一个；时间线一直都在。
   - 第一次打开时选中图最多的那一类；面板开着期间，记住用户选过的类。
4. **内容**：
   - **分类视图**：一个名字一张卡片，显示封面、名字和张数；按最新一张图的时间排，最新的在前。
     - 封面：角色用最新的一张设定图，没有设定图就用最新出镜的一张；其他类用最新的一张。
   - **点开卡片**：上面是“返回”、名字和张数，下面是这些图：
     - 角色：先放设定图，再按场景放这个角色出镜的图，最近有新图的场景排在前面。
     - 场景：这个地点的所有图，最新的在前。
     - 界面：按页面分组，最新的在前。合写一行的连续截图叠成一摞，标上张数，点开再展开。
     - 文档：按页码排。
     - 其他：最新的在前。
   - **时间线**：就是现在的按轮浏览。每一轮标题末尾仍有整轮勾选的小方框，最新一轮在最上面。
   - **没有特征行的图**（升级前的图，或者模型没写）：放进“其他”里一张叫“未归类”的卡片，时间线里照常显示。
5. **搜索时**：搜索框里有字，分类按钮和卡片就先收起，改成显示一整片搜索结果：跨所有类别，最新的在前。清空搜索就回到原来的视图。
6. **用量卡片**：从顶部挪到底部，收成一行，例如“下一条消息约 1.7 MB · 少发 77%”。点开后的内容和现在一样。
7. **底栏**：一句说明加“自动选图”开关，不变。

### 缩略图和预览

- 小标记和角标不变：每轮都发、刚取回、不发送、无法取消、已不在上下文、压缩前；PDF 第 N 页、网页。
- **变灰只在手动模式下**：表示下一条消息不发这张图。自动模式下换成占位是常态，不再变灰（Claude 2026-11-22 提议）。
- 预览里加一个“复制编号”按钮，方便在对话里说“用 IMG-015”。
- 点编号按钮（“模型需要”“最近一轮模型取回”里的）：先切到时间线，再滚到那一张，其余做法和现在一样。
- 卡片上显示模型起的名字；特征行的其余部分和评价仍然不显示，只用来搜索（v0.8 的规则只放开名字这一项）。

### Claude 桌面版

用同一个面板，和 v0.8 一样有几处不同：没有停用按钮，没有子代理和旁聊那一行，没有 PDF 和网页的角标。

## 4. 一轮之内的截图

- **范围**：只在开着自动选图时做，手动模式不变。子代理和旁聊本来就按自动选图管，也照做。
- **哪些图**：这一轮里由工具返回的图，截图最常见。
  - Claude：Read 以外的工具。
  - Codex：view_image 和生图以外的工具。
  - 用户上传的图、用 Read 或 view_image 看的文件、生成的图，在它们出现的那一轮都不动。
- **什么时候换**：
  - 这一轮里最新的 5 张保留原图；更早的攒够 10 张，一次全部换成占位。这样缓存每 10 张截图才断一次，不是每一步都断。
  - 这两个数到关卡 2 再调。
  - 一轮里不超过 14 张工具图时，什么都不变。
- **占位**：和之前各轮的占位一样（编号、来源、轮次、尺寸），标明是“本轮”。还没有特征行，因为特征行要到这一轮结束才写；模型需要时用 `cam_view_image` 取回原图。
- **特征行**：这一轮结束时照常写，连续截图可以合写一行（第 2 节）。
- **补写特征行**（v0.10：被打断那一轮的新图，下一轮再发一次让模型补写）：截图多的一轮被打断后，只把最后 5 张再发一次，其余的不补。computer use 一轮几十张，全部重发得不偿失。
- **缓存**：
  - Claude：引擎为下一批要换的图提前放好读缓存的位置（`anthropic-messages/cache.ts` 的 prepare），放在这一轮里第一张还没换的工具图前面。
  - Codex：缓存按前缀自动匹配，不用放标记。
- **思考记录**（Claude）：一轮之中换掉一张图，这一轮里在它之后的思考记录就对不上了。引擎现在的做法是去掉这些对不上的思考记录（`anthropic-messages/thinking.ts`），模型可能重新思考。这对长时间的 computer use 有什么影响，由关卡 2 来查。

## 5. 要先验证的事（关卡）

每个关卡通过了，才做对应的部分；没通过，就回来和用户商量。

1. **模型会写新格式**：
   - 测试：Codex 用 gpt-6-sol，推理强度 low；Claude 用 Haiku 5.5，推理强度 low；中英文都测。场景里有两个角色（其中一个是猫）、三个地点、一串截图和一页文档。
   - 看四点：类别选对（设定图写角色，关键帧写场景，截图写界面）；同一个角色每次用同一个名字；角色段写对；只有截图合写成一行。
   - 通过的标准：九成以上的行能解析出正确的类别，同一个角色从头到尾一个名字。
   - **结果（2026-11-22）**：
     - Codex 没跑成：两次 sol 自测（中英文）的每一轮都被 Codex 额度拦下。用户定：这一版在 Claude 上测，Codex 由用户之后手动试（第 11 节）。
     - Claude：脚本 `spike/src/v12-claude-features.ts`，用 Claude Code 命令行加载这个分支的插件，账号是评测专用配置。Haiku 5.5（中文 1 次、英文 6 次）和 Sonnet 5.5（中文 1 次），推理强度都是 low，每次 6 轮。
     - 写对了的：九张图里，模型拿到编号的每一张，类别、名字、角色段和评价都写对了。猫记作角色，名字用用户起的；关键帧写成 `场景:书房｜林夏、阿橘｜…`；四张截图都写成界面；合同页写成文档；色板写成其他。正文里没提这些行，也没有一条回复以记录行结尾。
     - 发现一：Claude Code 的命令行版有时在请求发出之后，才把会话的第一条消息写进记录文件。引擎等了 1.5 秒也没读到，第一轮的图就没带编号，模型也没收到特征行说明，这两张图一直没有特征行。8 次里有 4 次是这样。这不是这一版引入的问题（v0.10 已经见过）。修法：引擎记下这些图的内容；下一轮把它们带着“已提供，还没有特征行”再发一次，最多 5 张；并在这一轮用户消息后面加一句说明，点名这几张。只加说明标记时，Haiku 不补写；加上点名的说明后，晚到的那次补写上了。
     - 发现二：英文的文档行有时写成三段，第三段是更多特征（`document: lease p. 3 | scanned, red stamp | …`），会被读成角色。改为：界面和文档不读角色段。
     - 截图都写成了一张一行，没有合写；不影响分组。
2. **一轮之内换截图**：
   - 测试：一个脚本工具连续返回约 25 张截图，模拟一轮 computer use。
   - Claude：API 都接受（没有 400）；数清楚去掉了多少思考记录；模型照样把任务做完；只命中系统提示那一段的请求不超过 1 次。
   - Codex：用同样的工具跑一次自测，模型照样做完；需要之前的截图时，会用 `cam_view_image` 取回。
   - 没通过时：Claude 那边先不做，或者只对不保留思考记录的模型做，回来商量。
   - **结果（2026-11-22，Claude 通过）**：
     - 脚本是 `spike/src/v12-claude-screens.ts`，另有一个 MCP 服务 `spike/src/v12-screen-server.ts`，它的 next_page 每调用一次，返回设置向导下一页的截图，一共 25 页，第 9 页有红色警告框。测试用 Sonnet 5.5，推理强度 medium。
     - 全部 28 次请求都返回 200，没有退回原始请求，引擎也没有去掉思考记录。
     - 第 15 张截图时，前 10 张换成占位；第 25 张时，前 20 张换成占位。每次请求里这一轮的原图都不超过 14 张。
     - 这一轮里，从缓存读到的不足一半的请求只有 1 次，就是换批的那一次。
     - 模型翻完了 25 页，答对第 9 页有警告框。下一轮问第 3 页的进度条，它用 cam_view_image 取回原图，答“约八分之一”，实际是 3/25。
     - 模型自己用上了合写一行，例如 `IMG-010~IMG-020 界面:设置向导·第10~20页｜…`。
     - 花费 0.36 美元。
     - Codex 没测（额度用完），由用户之后手动试。
3. **面板做到关键节点，截图给用户看，等反馈再继续**：
   - 分类按钮和卡片；
   - 角色卡片和界面卡片点开之后的样子；
   - 搜索。
   - 开发页和 Claude 桌面版都截。

## 6. 公开评测

- **场景**：一部短片的关键帧，约 60 张图，12 轮左右。
  - 图片按真实出图的尺寸画：关键帧 1024×1536，视频帧 1920×1080。加上纹理和噪点，让文件大小接近真实出图。
  - 每张图的区别由脚本定（戴帽子、打伞、站位、偏暗、角落里的数字），可以自动判分，别人也能复现。
  - 多数图只在对话里：一部分是“用户”直接贴进来的；一部分由一个模拟的生图工具返回，只给图和一个资产编号，不存文件。另有少量磁盘上的图，作对照。
- **各组**：不装插件，以及 0.12。都用 Sonnet 5.5，推理强度 medium，全程不换。
- **压缩**：
  - 哪一组的上下文超过 10 万 token，脚本就给那一组发 `/compact`；提问之前，两组再各压缩一次。
  - 画出两组每一轮的上下文大小曲线。
  - 到 Claude Code 真实的压缩门槛时各要压缩几次，用实测的“每张图让上下文涨多少”推算，不另外花钱跑。
- **提问**：从压缩后的同一个点分叉出 2 个会话，每个会话各问约 10 题。题目分四种：
  - 只在对话里的图（贴进来的、生成的）；
  - 用户说过的评价；
  - 行动题：要求“用第 2 镜定稿那版再出一版”，看传给生图工具的资产编号对不对；
  - 磁盘上的图，作对照。
  - 判分照旧从严：回答里有不止一个答案，算“含糊”。
- **指标**：
  - 被迫压缩了几次；
  - 压缩后的答对率，对话里的图和磁盘上的图分开算；
  - 行动题对不对；
  - 最大一次请求，以及平均每轮的输入；
  - 花费和从缓存读的比例；
  - 名字一致的比例。
- **额度**（用户 2026-11-22：一次评测不能超过一周额度的 20%）：
  - 先试跑：两组各跑 3 轮，读出周额度和 5 小时额度涨了多少，推算全量要用多少。
  - 脚本里加一道闸：从开跑时的读数算起，周额度涨 15 个点就停。原来的“用到 90% 就停”保留。
  - 推算超了就缩小规模：先减少轮数（每轮多放几张图），再减到 1 个分叉。
  - 评测放在后台跑，Claude 只读汇总。
- **试跑时顺带查清两件事**：
  - 在 Sonnet 5.5 上，Claude Code 发一张图实际占多少 token。
  - Claude Code 决定自动压缩时，看的是 API 报回来的用量，还是自己估算的大小。如果是前者，插件在真实使用中也能推迟压缩；如果是后者，就推迟不了。结果决定 README 怎么写。
- **报告**：放进 `eval/` 下新的一个文件夹，中英两份。README 底部的那一小节换成新结果。
- **脚本（2026-11-22）**：
  - `spike/src/eval-v12-scene.ts` 定场景，沿用上次评测（`eval-long-scene.ts`）的短片和区别设计，图都放大 2 倍画（关键帧 1024×1536，约 3.5 MB）。
  - 26 张关键帧由模拟生图工具 `spike/src/eval-v12-gen-server.ts` 返回。同一镜只返回一次图，再要只给名字，不存文件。
  - 11 张三视图、设置页截图和简笔画直接贴进对话；14 张抽帧放在磁盘上，用 Read 看，作对照。
  - 每个分叉问 13 题：10 题问只在对话里的图，2 题问磁盘上的图，1 题是行动题。
  - `spike/src/eval-v12.ts` 负责运行：上下文超过门槛就 `/compact`，最后一轮之后再压缩一次，然后分叉提问。周额度比开跑时涨了 `--budget`（默认 0.15）就停下。`--quick` 只跑 3 轮、压缩一次、问 3 题。
- **试跑（2026-11-22，Sonnet 5.5，推理强度 medium，两组各 3 轮、压缩一次、1 个分叉问 3 题）**：
  - 流程都通了：生图工具出图、压缩、分叉、判分、行动题读出参考图。
  - 不装插件 3 题对 2 题：问角落数字的那题，压缩后它说“看不到 s02_v3.png，工具不会重新显示，也没有文件”。装插件 3 题全对，那题用 cam_view_image 取回了原图。
  - 花费按 API 价格：不装插件 0.34 美元，装插件 0.48 美元。这么短的一段，装插件那组从缓存读的比例还低一些（59%，不装插件 76%）。
  - 额度：两组合计，周额度停在 3%，没动到 1 个点；5 小时额度从 22% 到 24%。
  - 推算全量约是试跑的 5 倍，5 小时额度约 10 个点，周额度约 1 到 2 个点，远低于 20%，不用缩小规模。
- **全量（2026-11-22，用户同意后跑；Sonnet 5.5，推理强度 medium，门槛 10 万 token，2 个分叉，每个 13 题）**：

  | | 不装插件 | 0.12 |
  |---|---|---|
  | 门槛触发的压缩 | 1 次（第 14 轮后，110,671 token） | 0 次 |
  | 只在对话里的图，答对 | 8/20 | 20/20 |
  | 磁盘上的图，答对 | 4/4 | 4/4 |
  | 行动题，参考图对 | 2/2 | 2/2 |
  | 最大一次请求 | 110,671 token | 41,859 token |
  | 平均每轮的上下文 | 52,765 token | 27,607 token |
  | 从缓存读的比例 | 93.3% | 82.1% |
  | 花费（按 API 价格，含两个分叉） | 3.10 美元 | 3.01 美元 |

  - 不装插件错的 12 题，都是压缩之后答不上来：问只在对话里的图长什么样，它说摘要里没记、文件夹里没有、工具也不会再显示。其中 4 题被判成“错的数字”，是判分把“重发一次”里的“一”读成了 1，其实也是说不知道。
  - 不装插件答对的，是靠文字就能答的：定稿是哪版、用户说过太暗的是哪张、后来重发的那张是哪版、磁盘上的抽帧（它用 Read 重读）。
  - M2 判“含糊”：它答 s06_v1.png，又说它自己顺手多生成的 s06_v4.png 是 v1 的副本、也戴帽子。模拟工具从参考图出新版时，给的正是那一镜第一版的副本，所以它其实说对了，但按“只能有一个答案”的规矩不算。放宽算，不装插件是 10/20。
  - 装插件的 20 题，只有一题取回了原图，其余靠占位里的特征行答出：模型当时就把“整体很暗”“头戴黑礼帽”“左下角数字17”记进了特征行。这次没测到“必须取原图”的情况有多少。
  - 两组都在主会话里自己多生成过几版（不装插件 2 次，装插件 1 次）：没有人要求，是模型自己做的。
  - 额度：两组合计周额度 3% → 4%，5 小时额度 26% → 32%。
  - 汇总在 `local/eval-v12/2026-11-22/summary/summary.json`，每题的原文在两组的 JSON 里。

## 7. 做法

- `core/notes.ts`：解析类别、名字、角色段和合写的编号范围；按第 2 节的表认旧格式。
- `core/words.ts`：重写特征行说明（中英文）；占位加上“本轮”。
- `core/session.ts`、`core/plan.ts`：自动选图的选择加上这一轮的工具图（5 张、10 张这两个数）；限制补写时重发的张数。
- `adapters/claude/engine.ts`、`anthropic-messages/cache.ts`：为下一批要换的图提前放好读缓存的位置。
- `proxy.ts`、`core/session.ts`、`anthropic-messages/rewrite.ts`（关卡 1 发现一）：记下发出时还没有编号的图，下一轮再发一次，并点名要它们的特征行。
- Codex 的接入层：选择规则在核心层，接入层只需要把这一轮的工具图交给核心层。
- `panel/panel-state.ts`：每张图带上类别、名字、角色和合写的范围，去掉 `scene`。
- `panel/panel.html`：分类按钮、卡片、卡片详情、搜索、用量卡片挪到底部、自动模式不变灰、复制编号；中文、英文、日文三份文字表一起改。
- `spike/scripts/panel-dev.ts`：加三个合成任务：
  - 创作任务：两个角色（其中一只猫）、三个地点；
  - computer use 任务：40 张截图，其中有合写的行；
  - 文档任务。
- 自测：
  - `spike/src/v08-features-selftest.ts` 改成检查新格式；
  - 新加一轮之内换截图的自测；
  - 评测脚本 `spike/src/eval-*.ts` 加新场景。
- 文档：发布时一起改 spec、design、README（面板截图和评测结果）和 CHANGELOG。

## 9. 不做

- **PDF**，下一版做：整份读进来的 PDF 文档块换成占位，模型按“文件＋页码”取回；源文件和扫描件分开处理。见 2026-11-22 的实测：Claude Code 整份读 PDF 时发出的是一个文档块，插件现在不处理。
- 在面板里打开图片所在的文件夹，或者另存原图。
- 合并卡片：等真的出现同一个角色被叫成两个名字，再做。
- 让用户修改名字或特征行。
- 给模型的缩略图拼版：和 PDF 一起，下一版做。
- 其他平台的面板，以及在终端版用 `/cam` 打开浏览器面板。

## 10. 验收

1. 两个平台的模型都按新格式写特征行，能正确解析；旧任务的图照样归类。
2. 面板的分类、卡片、卡片详情、搜索和时间线，在 Codex 和 Claude 桌面版里都按第 3 节工作，用户看过截图。
3. 一轮几十张截图时，每次请求里这一轮的原图不超过 14 张；API 都接受，任务照样做完，缓存命中不下降。
4. 评测发布到 `eval/`，额度没有超过约定。
5. 原有的测试和自测不退化。

## 11. 用户的决定

2026-11-22：

9. 发布 v0.12 时，一起合并外部贡献 [PR #21](https://github.com/chipfighter/context-attachment-manager/pull/21)（IbukiFuko）。它修的是：Codex 任务回退后留下几条完整的分支时，面板读不出图；现在去 Codex 的状态数据库（只读）查当前用的是哪一条。
   - 2026-11-22 核对过：它只改 `codexconfig.ts`、`thread-index.ts` 和对应的测试，这一版和 `fix/engine-stability` 都没碰这几个文件；和 `fix/engine-stability` 试合并没有冲突；放到这一版的改动上，全部 355 个测试通过；三个平台的 CI 都过了。
   - 只在有几条分支时才去读数据库，平常的任务不受影响；读不出来就退回原来的报错。
   - 用到 Node 自带的 SQLite，加载时会在 stderr 打一行“实验功能”的警告，不影响使用。
8. 发布 v0.12 时，一起合并分支 `fix/engine-stability`。这是另一个会话做的引擎稳定性修复，已经测完：到上游改用 HTTP/2 并定时发 PING，用户的代理不会再掐断生图请求；引擎防崩溃；Windows 上引擎不再跟着关掉的插件服务一起退出。合并时 `rewriteClaudeBody` 的两个新参数（`missed`、`pre`）都保留。这两个参数按位置传，Node 又不做类型检查，所以合并后要核对 `proxy.ts` 里的调用，确认每个值落在对的位置。Codex 的 `rewriteBody` 末尾也加了 `pre`，同样要核对。合并后跑一遍全部测试，再加一条测试：同时传 `pre` 和 `missed`，确认两个都生效。这次改了引擎的启动方式，安装前先关掉 Codex，装完马上检查健康状态。
