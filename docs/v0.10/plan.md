# v0.10 方案：压缩和续接之后，照样拿回之前的图

> 状态：用户 2026-10-31 确认方案，让 Claude 按自己的安排做完（第 8 节）。代码和单元测试已完成，spec 和 design 已改；关卡 1–4 用本机回放验证通过，关卡 6 的大会话只有估算（系数按桌面实测校准过），关卡 5、7 的模型自测因为 Codex 用量到了上限没跑成；Claude 桌面实测（压缩、重启、改消息分叉）和长会话回放（关卡 8）已通过，回放发现的三处（第 2 节第 9 到 11 条）已修。公开评测（第 6 节）2026-11-01 跑过一次，评测里又发现并修了两处（第 2 节第 12、13 条）；报告先留在本机，等 Claude 会话的提示缓存命中问题改好、重跑之后再发布（第 8 节第 7 条）。这几项通过之前不发布。起因是用 5 个真实会话评估图片检索（会话内容只在本机，不进仓库）。规格以 [spec.md](../spec.md) 为准，实现见 [design.md](../design.md)。

## 1. 背景与目标

评估的结论：模型按编号选图很准，约 55 次取图只错 1 次，还是错在版本判断上。问题出在底层，压缩和续接让图和特征行丢了或挂错了：

- **Claude，压缩当场。** Claude Code 2.1.304 起，压缩时会原样保留最后几条消息（压缩记录的 `compactMetadata.preservedSegment`，也可能是 `preservedMessages`）。它读记录时，把保留的消息改接到摘要后面，再删掉压缩点之前的记录；文件里存的却是改接之前的样子。插件照文件里的父子关系连对话链：
  - 新消息接在保留的消息上时，对话链绕过了压缩点，插件认不出压缩，压缩前的图一张都没放回（一次真实压缩：94 张）；
  - 新消息接在摘要上时，插件能认出压缩，但把保留的消息算在了压缩点之前。
- **Claude，续接。** 在 Claude 桌面版里改一条之前的消息再发送（回退）时，桌面版从那里分叉出一个新会话、新开一个记录文件（日志里是 `resumeSessionAt` 加 `forkSession`），Claude Code 只把压缩点之后的记录写进去。只是重启进程（归档再恢复、内存紧张时被暂停）用的还是原来的会话和记录文件（2026-10-31 查桌面版日志：21 次分叉都换了会话 id，只重启的没换；实测也是这样。原来写成“每次重启进程都续接成新会话”，不对）。插件只读当前文件，于是：
  - 压缩前的图放不回；
  - 编号从头重排，对话里按旧编号写的特征行和评价挂到了别的图上（一个真实进程里，带特征行的占位 30 个全部挂错）；
  - 旧的取回副本对不上新编号，被当成新图另编了号。
- **Claude 的勾选不沿用。** 勾选、每轮都发和自动选图开关按会话 id 存，续接和分叉之后都失效。
- **Codex。** 编号是稳定的。但 Codex 压缩时只留下系统和开发者消息、全部用户消息和一段插件读不了的加密摘要，生成的图、查看的图、工具返回的图连占位一起从请求里消失（一个真实任务压缩时 43 张图只剩用户上传的 10 张）。模型凭编号仍能取到它们，只是看不到。

目标：

1. 两个平台压缩之后（Claude 还包括续接之后），之前的每张图都带着编号、特征行和评价留在请求里，模型能照样拿对；勾了每轮都发的（手动模式下是勾着的）照发原图。
2. 编号在压缩、续接、分叉前后都不变。老会话里按重排编号写下的记录行换算回来，落到对的图上（用户 2026-10-31 要求老会话也精确找回）。
3. 代价可以接受：引擎内存和每条请求多出的 token 都有上限，见第 3 节。

不做（用户 2026-10-31 定）：

- 生成时交给生图工具哪些参考图：不归插件管。
- 改检索算法：先修底层，修完以后小规模回放，哪里错了再针对那一处改。
- 截图（浏览器、电脑操作）的专门规则：另议。

## 2. 规则

### Claude

1. **对话链照 Claude Code 的规则连。** 对最后一个带保留信息的压缩点：保留的消息接在摘要后面；原来接在摘要上的、接在被删记录上的消息，都接到最后一条保留消息后面。和 Claude Code 不同的是，压缩前的历史不删：压缩点往前接到第一条保留消息原来的前一条，压缩前的图照 v0.5 的做法放回摘要后面。没有保留信息的旧格式不变。
2. **续接的记录文件往回接。** 记录文件从压缩点开始、前面没有历史时，找到原来的记录文件，把压缩点之前的历史接上：
   - 先看摘要里 Claude Code 写的那句 “read the full transcript at: …”（取最后一处），只认 Claude 的 projects 目录里、含同一个压缩点的文件；
   - 不行再在同一个项目文件夹里按压缩点找；
   - 原来的文件也可能是续接来的，就一层层往回接；
   - 只读；找到的记下来，不反复找；
   - 找不到时照现在的做法，但对不上的记录行不认（见第 3 条），宁缺不错。
3. **老记录行换算回来。** 修复之前写下的特征行、评价，以及取回副本前面那行字，用的是写它们的那个进程当时的编号，也就是从那个进程所在记录文件的起点数起的编号。插件找出同一会话的全部记录文件（同一项目文件夹里，第一条对话记录是会话起点或某个压缩点的那些），按创建时间判断每条记录行是哪个进程写的，再经图片本身换算到恢复后的编号。这个版本第一次运行以后写下的不用换算：和 v0.6 的 auto-default.json 一样，记下这个版本第一次运行的时间。
4. **勾选沿用。** 续接和分叉出来的会话还没有自己的勾选时，沿用上一个会话的勾选、每轮都发和自动选图开关；分叉照 Codex 的规则，只沿用分叉那一刻之前的。之后各管各的。

### Codex

5. **压缩后放回被丢掉的图。** 请求里有 Codex 的压缩项时，把压缩之前、请求里已经没有的图按编号放在压缩项后面：没勾每轮都发的写成一行（见第 6 条），勾了的发原图，带“已提供”标签；后面跟一条说明。手动模式同理：勾着的发原图，没勾的放一行。没有被丢掉的图时，请求不变。

### 两边

6. **紧凑写法**（只用于压缩后放回的那一段）：一张图一行，写编号、名称、来源、轮次、特征行和最近 3 条评价，例如“IMG-041｜exec-….png｜查看｜第 28 轮｜海边栈道｜半身中景，白衬衫，回头｜评价：第 29 轮“光太硬了””，没有名字的写“-”，清单第一行说明各列；怎么取图在说明里讲一次，说明里不再把图列第二遍。
   - 原因：原来每个占位都重复一句“需要原图时调用 cam_view_image…”，说明里又把全部图列一遍。一个有 127 张压缩前图片的真实会话，照原写法每条请求要多约 1.7–2.0 万 token（压缩后第一条请求的约 16%–18%）；紧凑写法加说明约 0.7–0.9 万（按桌面实测校准的系数估，见关卡 6）。
   - 别处的占位（图在原位被省略的）不变。
7. **补写和更正特征行**（用户 2026-10-31 采纳了方向，做法见第 8 节）：
   - 补写：被打断的那一轮，新图没写上特征行。被打断那一轮里还没有特征行的图，下一轮再发一次，标签写“已提供，还没有特征行”。
   - 更正：模型发现特征行写错了（比如用户指出），写一行 `[//]: # (cam IMG-005 更正：…)`，替换原来的特征行。
   - 这一条改的是特征行说明，按 AGENTS.md 跑自测。
8. **截断按宽度算**（做的时候回放发现，Claude 定）：特征行和评价超长时，原来按界面语言数字符截断（中文 30、英文 100），中文界面里模型写的英文特征行被截到只剩地点。第 6 条那个会话的 180 条特征行里 91 条是英文，全被截成“cafe storefront morning |…”这样，51 条截完和别的行一模一样；压缩之后清单是模型看到这些特征的唯一地方，它就分不清这些图。改成按宽度算，和界面语言无关：中日韩文字一个算 1，其他字符算 0.3，特征 30，也就是 30 个汉字或 100 个字母（评价见第 10 条）。截完相同的从 51 条降到 6 条（127 张里能分开的特征行从 76 条升到 105 条），放回的一段多约 0.2–0.28 万 token（按校准后的系数）。原位的占位用的是同一个截断，也跟着变。

下面三条是长会话回放测试发现的（2026-10-31，用户定三个都修；测试做法和结果只在本机，见第 3 节第 8 条）：

9. **并行读图乱序时照样编号**（插件 bug，v0.4 起就有）：模型同时读几张图、结果回来的顺序乱了时，对话会从前面某个调用的结果接着走，后面的调用记录不在对话链上，插件认不出它们的图。这些图没有编号，每轮照发原图，压缩后丢失，也取不回。改成：同一次回复的几次调用带同一个消息 id，不在链上的也接回来，图按调用顺序编号。补上编号后，排在它后面的图编号后移，修复之前写下的记录行按当时的编号换算（第 3 条的做法，旧编号跳过这些图）；编号规则的版本记在 `stable-ids.json` 里，规则变了，第一次运行的时间重新记。
10. **评价和特征行一样长**：评价原来截到 15 个汉字，长会话测试里一条 18 个字的评价在清单里只剩前半句，压缩后模型看不到后半句说的问题。评价是用户的原话，一个会话没几条，上限改成和特征行一样，30 个汉字或 100 个字母。
11. **清单里标出同一张图**：用户重发同一张图时，插件已经认得出是同一张，但清单列成两行、各写各的特征。改成后面那行写“同 IMG-108”，不再重复特征。
12. **等记录文件写完再改写**（公开评测试跑时发现）：Claude Code 有时在把这一轮刚读的图写进记录文件之前就发出请求，插件认不出这几张图，原样发出、不带编号，模型这一轮没法给它们写特征行（试跑里一轮 3 张；用户本机日志 8904 次请求里有 119 次，下一次请求才认出）。改成：请求里模型最近一次回复之后有认不出的图时，引擎每 100 毫秒重读一次记录文件，最多 1.5 秒；认出了就照常改写。一张一直认不出的图只让一次请求多等这一下。
13. **压缩后照常看新图**（公开评测发现）：说明里“不要用其他工具去读取图片文件”本意是被省略的图要用 `cam_view_image` 取。评测第一次跑 0.10 时（Haiku 5.5，推理强度 low），压缩后模型把它当成所有图，用户后面 5 轮让它看的图一张都没读。改成只说被省略的（Codex 的压缩说明里是清单里的）图，并写明用户新让它看的图照常去看；重跑后每轮都照常读图。这是发给模型的措辞，按 AGENTS.md 要跑 Codex 的 `v01-placeholder`、`v01-needs`、`v03-auto` 自测。

## 3. 要先验证的事（关卡）

每个关卡通过了，才做对应的部分；没通过，就回来和用户商量。

1. **改接覆盖到的格式**：`preservedSegment` 和 `preservedMessages`，新消息接在保留消息上、接在摘要上两种形状。用合成记录，再加真实记录回放（本机，结果只放 `local/`）：压缩前的图都认出来，编号和原始文件一致。
   - 原型（2026-10-31，没改插件，只在内存里改接后交给现有的索引代码）：一次真实压缩从认出 0 张变成 94 张。
   - 结果（最终代码，2026-10-31 回放）：通过。那次压缩认出 94 张；两个真实会话（6 个、3 个记录文件）里，同一张图在每个文件里的编号都一样（0 处不同）。
2. **往回接**：摘要里的路径、按压缩点找、往回两层、分叉、原文件不在。真实回放：编号和原始文件一致，特征行一条不挂错。
   - 原型：续接一层和两层都接上了，压缩前的图编号、特征行和原始文件里一样。
   - 结果：通过。最长的会话 210 张图，压缩前的 127 张都接回来了，编号和原始文件一致；抽查原来挂错的特征行，都回到了对的图；17 个取回副本都认回原图（原型里有 9 张被当成新图）。
3. **换算**：真实回放里，换算过的特征行中“写下的轮次等于图出现的轮次”的比例，不低于从没被打乱过的那段，并且抽查无误。
   - 原型：换算的 80 条里 73 条一致；从没被打乱过的那段是 103 条里 71 条，不一致的都是晚了 1–4 轮才写（后台任务完成算新的一轮）。约 3 条（2%）明显不对，要查清。
   - 结果：通过。换算过的 77 条里 73 条写在图出现的那一轮，4 条晚 1–4 轮；从没被打乱过的 103 条里 71 条、晚的 32 条；没有挂错的。原型里那 3 条“明显不对”的，是同一个文件前后看了两次、模型两次写了一样的特征行，统计时按文字找到了前一次，不是换算错。
4. **内存和时间**：最长的真实会话（9 个记录文件、219 张图），引擎的堆内存比现在多不超过 80 MB；第一次建索引不超过 2 秒；之后每条请求的改写，耗时不超过现在的两倍。
   - 原型照原样读：堆内存从 83 MB 到 268 MB，多出的几乎都是旧文件里的图片数据，所以要改成用到时再从文件读（发原图、取图、面板缩略图时）。第一次建索引 1.7 秒，之后每条请求 9–12 毫秒（现在 6 毫秒）。
   - 结果：通过。旧文件只留压缩点之前带 uuid 的记录，图片数据留在磁盘上、用到时再读：堆内存 83 → 145 MB（多 62 MB），第一次建索引 1.8 秒；每条请求重建约 10 毫秒，同一请求里再读走缓存，约 0.5 毫秒（现在是每次都建，3 次共约 6 毫秒）。
5. **Codex 放回的位置**：压缩项后面能不能插；插成开发者消息还是用户消息，模型才把它当真；连续两次请求里这一段逐字节相同，缓存接得上。用 app-server 的 `thread/compact/start` 做探针验证。
   - 结果：未完成。按真实压缩记录重建的请求（本机回放）和单元测试里，放回的一段在压缩项后面（说明是开发者消息，原图在后面一条用户消息里），两次请求逐字节相同。探针（`spike/src/v10-compaction-selftest.ts`）没跑成：Codex 用量到了上限，2026-11-04 15:35 恢复。
6. **token**：实测压缩后的请求，按 API 返回的用量算，不按估算。130 张图的 Claude 会话、33 张图的 Codex 任务，多出的不超过请求的约 7%，Claude 压缩后的头几条请求可到约 9%（原定 6% 和 3%；用户看了估算后放宽，准确度和信息别丢太多更要紧，见第 8 节）。
   - 结果：大的会话只有估算，系数用 Claude 桌面实测校准过：拿模型回复的长度对照 API 报的 output token，汉字一个约 1.25–1.35 token，其他字符约 0.36–0.5（原来按 1.0–1.5、0.25–0.3 估，非汉字偏低；整条请求按原系数估 5.4–6.5 万，API 报 7.5 万）。Claude 那个 127 张的会话，放回的一段约 7.3–9.1 千 token（清单 6.0–7.7 千、说明 1.3–1.4 千），原写法约 1.7–2.0 万；这个会话续接后第一条请求是 9.1 万 token，这时约占 7%–9%，对话变长后下降，请求到 15 万时约 5%–6%，到中位数 31 万时约 2%–3%。比原定 6% 多出的部分主要来自第 2 节第 8 条（英文特征行不再截短）。Codex 那个 33 张的任务约 1.2–1.7 千（说明 0.24–0.34 千、清单 0.98–1.33 千），压缩后第一条真实请求是 44,893 token，约占 2.7%–3.7%，其中编号式的文件名约 0.2–0.3 千（第 8 节第 5 条）；Codex 的分词不同，没有校准，按偏高的系数算也不到 4.5%。桌面实测的小会话（4 张图）：压缩后第一条请求 75,099 token，放回的一段约 1.2–1.8 千。
7. **模型照样会取、取对**：改成紧凑写法、放回之后，Codex 自测（gpt-6-sol，推理强度 low），Claude 桌面测试会话（Haiku 5.5），中英文都测。
   - 结果：Codex 部分未完成，10 组自测（新的 v10-compaction 和 v08-features、v01-placeholder、v01-needs、v03-auto，各中英文）都因 Codex 用量上限（HTTP 429）没跑成，建的测试任务都已归档。
   - Claude 部分通过（2026-10-31，桌面测试会话，Haiku 5.5，推理强度 low，用户手打 `/compact`、手动回退）。第一次桌面实测发现，v0.9.0 起 Claude Code 2.1.309 不加载插件的 mod（它用变量传环境变量的名字），Claude 会话的请求根本不经过插件；修好后重测：
     - 压缩当场：摘要后面放回了 4 张图的清单，特征行都在；模型按编号取回 IMG-002，答对细节。
     - 归档再恢复（只重启进程，还是原来的记录文件）：请求照样经过插件，清单和编号不变，这一段走缓存。
     - 改一条之前的消息再发送：分叉出新记录文件，里面只有压缩之后的记录；插件接回原文件，编号仍是 IMG-001 到 IMG-004，清单逐字不变；新进程里按编号取回 IMG-003，答对。
8. **长会话回放**（用户 2026-10-31 提议）：把用户一个真实的长会话照原话和原图逐轮重放给新的测试会话（Sonnet 5.5，推理强度 medium），在真实会话压缩的位置手打 `/compact`，每次压缩后照用户的问法问几张旧图。会话内容只在本机。
   - 结果：回放到第 50 轮（152 张图，用户叫停），压缩两次（94 张、127 张时），压缩后 12 道题编号全对，没有一次取错图；清单够用时不取图，要比较时一次取几张候选。压缩后第一条请求里放回的一段约占 7.8%–8.8% 和 9.7%–10.9%（测试的文件名比真实的长）。发现第 2 节第 9 到 11 条的问题。

## 4. 做法

- **认记录**（`claude-index.ts`）：
  - `activeChain` 照第 2 节第 1 条改接；
  - 往回接：找原记录文件、逐层接、记住找到的文件；
  - 旧文件里的图片数据不常驻内存：记下位置，用到时再读；
  - 换算：找出同一会话的记录文件、判断每条记录行是哪个进程写的，换算记录行和取回副本前面那行字。
- **勾选**（`selection.ts`）：Claude 会话没有自己的勾选时，找到上一个会话沿用。续接的，上一个会话是同一会话里的上一个记录文件；分叉的，Claude Code 在复制过来的记录里留着原会话的 id。
- **Claude 的请求**（`proxy.ts`、`claude-rewrite.ts`）：压缩后放回的那一段改成紧凑写法，说明里不再列全部图。
- **Codex 的请求**（`proxy.ts`、`rewrite.ts`）：认出请求里的压缩项，找出压缩之前、请求里已经没有的图，放回压缩项后面。
- **措辞**（`rewrite.ts`）：新增中英文的紧凑行和两条说明；按第 2 节第 7 条改特征行说明。
- **面板**不用改：它读同一个索引，续接后的会话会重新列出压缩前的图，编号和原来一样。做完截图看一下。
- **更新时的过渡**：更新插件后，开着的 Claude 会话要重开一次，因为旧进程里的取图工具还按旧编号找图。写进 CHANGELOG。
- **文档**：发布时一起改 spec（核心概念、选择规则、占位符、Claude 一节的“压缩之后”、非目标）、design（第 3、4、12 节）、CHANGELOG，以及 AGENTS.md 的入口。
