# v0.5 方案：Claude Code 压缩后保留图片

> 状态：用户 2026-10-12 确认；开发和实测完成（第 5 节），2026-10-13 发布 v0.5.0。规则由用户 2026-10-12 定（见第 2 节）。规格已写进 [spec.md](../spec.md)（标着 v0.5），实现见 [design.md](../design.md) 第 12 节。

## 1. 背景与目标

Codex 每次请求都带着任务里全部的历史图片，插件在那边按勾选替换。Claude Code 不一样：上下文到了压缩线（手动 `/compact` 或自动压缩），它把旧历史换成一段文字摘要，压缩前的图一张都不再发给模型；图太多时还会直接报错，提示用户压缩或开新会话。用户要求过“只去掉部分图片、不整段压缩”，被以不计划做关闭（anthropics/claude-code#37461，另见 #52224）。

目标：Claude Code 压缩之后，用户压缩前的勾选照样有效。勾着的图在压缩后照样发给模型，取消的照样不发；用户和模型都还能按编号用回压缩前的图。不换会话，对话照常进行。

Codex 不变：Codex 不会在压缩时丢图。

## 2. 规则（用户 2026-10-12 定）

1. **保留勾选**：压缩前勾着的图，压缩后照样发送；取消的照样不发。自动选图开着时，“固定发送”的图照样发送，其余的照旧由模型按需取回。用户在面板里随时可以改，从下一条消息起生效。
2. **补在哪**：照样发送的压缩前的图，放在压缩摘要后面，按编号排好、各自标上编号、名字和轮次。位置固定，勾选不变时请求逐字节相同，缓存能续上。实测后（2026-10-12）不发的那些也在这里放占位文字，和别处一样（第 5 节）。
3. **告诉模型有哪些旧图**：压缩后附一份压缩前的图片清单（编号和名字，不含图）。模型需要某张没发的图时照常写“需要 IMG-xxx”；开着自动选图时用 `cam_view_image` 取回（现在就能取，原图还在本地）。实测后清单和说明放进摘要那条消息后面的系统消息，和 v0.4 的说明一样（第 5 节）。
4. **不替用户做决定**：不做自动保护。补回的图太多、请求被拒绝或 Claude Code 又压缩时，由用户在面板里少勾几张或切到自动选图；面板照常显示请求大小的预估。
5. **改一条硬约束**：现在引擎“只替换用户取消的图片”。v0.5 起，引擎也会把用户勾选、但 Claude Code 因压缩不再发送的图，从本地会话记录里取出来补进请求。其余内容仍原样转发。

## 3. 事实与依据

- **原图都在本地**（2026-10-11 在用户本机核对）：Claude Code 的会话记录只追加不删除。一个压缩过两次的会话记录里有 17 张图，16 张在最近一次压缩之前，完整的图片数据都还在。插件现在就从这里读图：压缩前的图在面板里列着（标“已不在上下文”），自动选图开着时模型也能按编号取回。Claude Code 只在定期清理旧会话时删除记录（第三方资料说默认 30 天），那时会话本身也没了。
- **压缩后的记录**（同一会话）：先是一条压缩分界（`compact_boundary`，用 `logicalParentUuid` 接上压缩前的历史），然后是一条用户消息，内容是摘要（`isCompactSummary`），之后是 `/compact` 命令本身的几条记录和重新附上的文件。插件的索引已经能跨分界编号，压缩前的图编号不变、标着 `compacted`。
- **缓存**：模型每次请求都重新处理整段上下文，但前缀和上一次完全相同时会命中提示缓存，按约 1/10 的输入价计费（Opus 5.5 是 1/20），写入缓存贵一些（5 分钟 1.25 倍，1 小时 2 倍；Claude Code 用 1 小时）。缓存省钱不省空间：补回的图实打实占上下文窗口。补回的位置固定，所以只在压缩后的第一次请求按全价算，之后命中缓存。
- **新账号的思考校验**：补图是对摘要之后内容的改动，之后产生的思考按 v0.4 的做法处理（引擎记下实际发出的内容，去掉对不上的思考）。
- **已知的显示问题**（v0.4.0）：压缩后如果下一条请求里一张图都没有，面板会把压缩前的图当成“还会发送”。v0.5 改了压缩前图片的显示，这个问题一并修掉。

## 4. 做法

- **索引和勾选**（`claude-index.ts`、`selection.ts`）：不变。压缩前后的图编号、键都不变，勾选按键保存，所以压缩后勾选自然还在。
- **改写**（`claude-rewrite.ts`、`proxy.ts`）：
  - 认出压缩后的请求：请求里有一条用户消息的文字等于会话记录里最近一次摘要（`isCompactSummary`）的文字，并且最近一次压缩之前有图。
  - 在摘要后面插入，就在那条消息里、摘要文字之后（实测见第 5 节）：压缩前的图按编号排开，照样发送的每张前面一行标签、后面是原图，不发的是占位文字。紧接着的系统消息里是说明：压缩前的图片清单（中英文两份，跟着现在的语言），这次没发哪些、怎么要回；有图没发时前面是完整的“上下文管理说明”，后面消息里的占位文字只再跟一段短说明。Claude Code 已在那里放了系统消息时并进去。勾选不变时这两条消息每次都一样，位置固定，不碰工具调用和结果的配对。
  - Claude Code 自己生成摘要的那个请求不用特别处理：它和普通请求一样带着全部历史和图，照常改写（第二次压缩时，里面同样补上第一次压缩前的图）。这样它的前缀和上一个请求一致，能命中缓存，写摘要的模型看到的图也和对话里一致。
  - 其余规则照旧：取消的图换占位符、说明消息、思考记录的处理。
- **面板**（`panel-state.ts`、`panel.html`）：压缩前的图照常可以勾选。勾着的显示为照样发送、计入请求预估；取消的显示“不发送”。行上加一个“压缩前”标记，说明它是补在摘要后面发的。界面改完截图给用户看。
- **取图工具**：不变，已经能取压缩前的图。

## 5. 实测结果与待确认

2026-10-12 用开发引擎在桌面测试会话里实测（Claude Code 2.1.295，Haiku 5.5）：读了三张图，用户输入 `/compact`，再问一句。

1. **压缩时的请求**：和普通请求一样带着系统提示、全部 177 个工具和思考设置，内容是到这时为止的历史，最后一条用户消息末尾加了一段 “CRITICAL: Respond with TEXT ONLY…” 的写摘要要求。三张图原样在里面，没有被换成 “[image]”（第三方资料说的去图，在这个版本上不成立）；最后一条回复没带上。回复是 `<analysis>` 加 `<summary>` 的摘要。所以写摘要的模型看着图写，这个请求照常改写即可（第 4 节）。
2. **压缩后的请求**：第一条是用户消息，内容是一整段字符串的摘要；接着一条空的系统消息；然后是压缩前的最后一条回复，原样保留；再往后是新的一轮。一张图都没有，模型凭摘要文字回答。补图的位置定在第一条消息里、摘要文字之后。
3. **自动压缩算不算补回的图**（观察，不加保护）：Claude Code 记进会话记录的用量是 Anthropic 返回的，含补回的图（英文测试会话最后一次 137,084 个输入 token，其中缓存读 135,621）。输入框旁的上下文用量是它自己的分类估算（172,023，其中“Messages”只有 125），不含补回的图。它按哪个数决定自动压缩没有查到，已写进 README：补回的图占上下文，Claude Code 的显示不算它们。
4. **Anthropic 对一个请求的限制**（[官方文档](https://platform.claude.com/docs/en/build-with-claude/vision)，2026-10-12 查）：图片数 200k 上下文窗口的模型最多 100 张，其他模型 600 张；每张最大 8000×8000 像素，一个请求超过 20 张图时每张的尺寸限制更严（边长不超过 2000 像素就没问题），历史里重发的和工具结果里的图都算；每张 base64 后最大 10 MB；整个请求最大 32 MB。已写进 README。

开发后的实测（2026-10-12，开发引擎，Claude Code 2.1.295，Haiku 5.5；真实图片的尺寸由测试图的生成代码确定，模型给的数都和它一致）：

5. **第一版的问题**：说明放在摘要那条用户消息里，没勾选的图直接不出现。补回过的图取消勾选后再问，模型说之前的数“没有依据，应当撤回”，并让用户重新提供图片；说明里点名“这次没提供”“不要收回”之后仍然这样。改成和 v0.4 一样：没勾选的放占位文字，说明作为系统消息跟在那条消息后面。在已经收回过的会话里复测仍然收回：模型照抄自己历史里的回复，那个会话测不出改动，只能在新压缩的会话里测。
6. **新压缩的会话**（中英文各一个，读三张图后用户输入 `/compact`）：
   - 勾着时问红方块边长：中英文都答 240 像素（看图答对）。
   - 取消勾选后问没描述过的黑色小方块：都说现在看不到、之前的描述仍然有效，单独写一行“需要 IMG-001”/“need IMG-001”，不让用户重新上传。
   - 问 240 还算不算：都说算，是看着原图说的，没有收回。
   - 勾回后再问：中文第一次没看到补回的图，说“这次消息里没有附上”。全部勾回时不发完整说明，模型不知道勾回的图回到哪里；说明里加上“勾回的图回到这里，不会出现在新消息里”后，中英文都答 48 像素（对）。但两边都说自己之前那句“需要 IMG-001”是错的：图现在排在它之前的回复前面，它以为一直都在。说明里又加了一句“当时看不到是因为被省略了”，再改成讲清这一段每次请求重新放；复测（这时会话历史里已经有这种自我纠正）中英文仍然这样说。回答本身都对，只是这句话不对，写进了 CHANGELOG；新压缩的会话里还没测最后这句措辞。
   - 用另一张图（c-tri.png）再走一遍取消、勾回：取消时中英文都通过；勾回后答对（48 像素），仍有上面那句自我纠正。
7. **自动选图**（中文会话）：压缩前的图都换成自动版占位文字，`cam_view_image` 在工具列表里。第一次问没测过的细节时，模型照会话里多次用过的方式写“需要 IMG-002”，没有取图；告诉它可以自己取之后，它调用 `cam_view_image` 取回 IMG-002，答对（48 像素）。下一轮取回的副本换成了“只在那一轮提供”的说明。固定发送 IMG-001 后，它在摘要后照样发出；模型又多取了一次这张已经在的图，答对。v0.4 的中文测试也有过一次多取。
8. **模拟新账号**（英文会话，推理强度 high，`CAM_EXPERIMENT_BLOCK_BINDING=error`）：第一次被拒（400），引擎去掉 3 段对不上的旧思考后重发，接受；取消一张后直接去掉对不上的思考，第一次就接受；全部勾回后，勾选相同时产生的那段思考对得上、放回去，接受，缓存读 135,621、写 1,461。回答都对。
9. **请求逐字节相同**：勾选相同的三个请求，摘要那条消息和后面的系统消息哈希相同；取消一张时不同。
10. **Codex 回归**：全部单元测试通过（192 个）；`v01-placeholder-selftest.ts` 中文、gpt-6-sol low 全部检查通过，测试任务已自动归档。v0.5 没有改 Codex 的措辞。

## 7. 验收

1. 压缩前勾着的图，压缩后下一条消息起照样发给模型，取消的不发；用户改勾选后从下一条消息起生效。**通过**（第 5 节 6 项）。
2. 补回的图在摘要后面，标着编号、名字和轮次；勾选不变时，连续两次请求的这一段逐字节相同。**通过**（第 5 节 9 项）。
3. 模型知道压缩前有哪些图：需要没发的图时按编号要；开着自动选图时能取回并看图作答。**通过，有两点遗留**：勾回后模型有时说自己之前“看不到”是错的（回答本身对）；手动用了很多次“需要 IMG-xxx”的会话切到自动选图后，模型先照旧要图，告诉它可以取之后才取（第 5 节 6、7 项）。
4. 面板正确显示压缩前图片会不会发送，请求预估包含它们。**通过**（截图见第 6 节 3 项）。
5. 新账号（模拟）上补图后对话不中断。**通过**（第 5 节 8 项）。
6. Codex 的功能和请求不变。**通过**（第 5 节 10 项）。
7. 中英文都实测，真实桌面会话，Haiku 5.5。**通过**。

## 8. 不做

- 自动保护：补回太多时不自动减少，由用户决定（用户 2026-10-12 定）。
- `/clear` 或新会话：那是另一个会话，不带过去的图。
- 子代理：仍只管主对话。
- 另存一份图片：直接读 Claude Code 的会话记录，不复制图片。
